# Faraway の自己アップデート

Faraway は、自分自身を更新できる。ただし「何でも勝手に」ではなく、次の安全策の範囲で行う。

## 方針（設計の核心）
- **人がレビューして main にマージしたコードだけが反映される。** Faraway は dev ツールで自分の改良を PR にできるが、マージはぴぐみさんが手で行う（main は保護）。マージされたものだけが、更新の対象になる。モデルが取得先を変えることはできない（`[update] remote_url` / `branch` は設定で固定）。
- **反映の前に必ず検証する**（稼働中の版には触れずに）: 自己検査（今の設定で組み立てられるか）→ テスト。通らない版は適用できない。
- **適用は承認が必要（R2）。** 管理画面の「承認」で内容（現在の版 → 新しい版）を確認して承認する。
- **失敗したら自動で戻る。** 切り替え後はスーパーバイザーが「試用期間」で見張り、新しい版が起動に失敗する・応答しない場合は、自動で前の版に戻し、その版を再試行しない。
- **戻せる。** 直前の版は残る。管理画面から「直前の版に戻す」（これも承認が必要）。
- **データと設定は更新で消えない。** 設定は `…\faraway\config.toml`、監査ログ等は `…\faraway\data\`（リリースの外）にある。シークレットは従来どおり `%USERPROFILE%\.assistant\secrets\`。

## しくみ
```
%USERPROFILE%\.assistant\faraway\
├─ supervisor.py      見張り役（標準ライブラリだけ。更新の対象外。手動でだけ更新する）
├─ config.toml        設定（更新で上書きされない）
├─ data\              監査ログ・ジョブなど（更新で消えない）
├─ releases\<sha12>\  リリースごとのコード（current.txt が指す版で動く）
├─ repo\              更新元の clone（取得専用）
├─ current.txt / previous.txt / pending.json / last_update.json / bad.txt
└─ logs\              準備（検証）のログ
```
1. **確認** `update_check`（R0）: 更新元の main を取得し、現在との差（コミット一覧）を調べる。手元のほうが新しい／履歴が分岐している場合は自動では更新しない。
2. **準備** `update_prepare`（R1）: 新しい版を `releases\.tmp-…` に展開 → 自己検査 → テスト（→ Windows では `Faraway.exe` のビルド）。全部通ったものだけ `VERIFIED` にして `releases\<sha12>\` に置く。失敗したら何も残さない（ログだけ `logs\`）。稼働中の版は一切変わらない。
3. **適用** `update_apply`（R2・承認）: `current.txt` を新しい版に切り替え、サーバーが終了コード 75 で終了 → スーパーバイザーが新しい版で起動し直す。
4. **試用期間**: 起動後 30 秒以上正常に動き、ヘルスチェックに応答したら「確定」。途中で落ちる・2分以内に応答しない場合は、前の版に自動ロールバックし、失敗した版を `bad.txt` に記録する。

## 初回のセットアップ（一度だけ）
今の開発用チェックアウト（`Documents\AITool`）を、最初のリリースとして取り込む。**取り込まれるのはコミット済みの内容（HEAD）だけ**。
```powershell
cd $HOME\Documents\AITool
python -m core.updater bootstrap
```
`%USERPROFILE%\.assistant\faraway\` ができ、`supervisor.py` と `config.toml`（今の設定のコピー。以後はこちらを編集する）が置かれる。表示された `start_command` で起動する:
```powershell
python "$HOME\.assistant\faraway\supervisor.py" --install-dir "$HOME\.assistant\faraway"
```
（これまでの `python -m api.server` の代わり。トークン・シークレットはそのまま使える。）
常駐させるなら、タスクスケジューラの起動時タスクでこのコマンドを実行する（`docs/app-setup.md` の自動起動の例を参照）。

**直接 `python -m api.server` で起動したサーバーは、確認・準備まではできるが、適用はできない**（再起動する人がいないため、安全に拒否される）。

## 使い方
- **Faraway に頼む**: 「Faraway を更新できる？」→ 確認 → 内容の説明 → 「検証して」→ 準備 → 「適用して」→ 承認要求（管理画面の「承認」で承認）。
- **管理画面の「更新」タブ**: 現在の版・更新元・試用期間・直近の更新結果、「更新を確認」「最新を検証して準備」「適用（承認を作成）」「直前の版に戻す」。
- **定期確認**: 6 時間ごとに自動で確認する（確認だけ。`update_available` が監査ログに残る。`auto_check_hours = 0` で無効）。
- CLI: `python -m core.updater status|check|prepare [--sha …]`

## アプリ（EXE）の更新
- サーバーは、準備のときにビルドした最新の `Faraway.exe` を配布する（`/api/client/windows`、認証必須）。
- `Faraway.exe` は、起動の少し後と 6 時間ごとに新しい版を確認し、あれば**トレイのメニューに「Faraway.exe を更新」が出る**（勝手には入れ替えない）。選ぶと、ダウンロード → サイズ・実行ファイルの先頭・**SHA-256 の照合** → 入れ替え → 再起動。古い版は `Faraway.exe.bak` に残る。
- `Faraway.exe --self-update [--yes]` でも実行できる。
- 限界: 配布元はこのサーバーなので、サーバーが乗っ取られると配布物も差し替えられる。そのため利用者の確認を挟み、サーバーは LAN/Tailscale の中に限っている。署名の検証は未実装。
- 画面（チャット・管理）はサーバーが配信するので、サーバーを更新すれば自動で新しくなる。PWA（Android）も同様。Android アプリ（APK）の自己更新は未実装。

## 検証（実機）
- `python scripts\e2e_selfupdate.py`（24 項目）: 本物のスーパーバイザー・サーバー・git で、正常な更新（確認→準備→承認→再起動→確定）と、「検証は通るが起動に失敗する版」の自動ロールバック・再試行の拒否・データの保存を確認。
- `python apps\windows\e2e_clientupdate.py`（13 項目）: 旧版の `Faraway.exe` を実際にビルドし、サーバー配布の最新版へ入れ替え。SHA-256 の不一致・サイズ違い・実行ファイルでないもの・認証なしを拒否。
- 単体テスト: `tests/test_updater.py`・`test_supervisor.py`・`test_update_tools.py`。

## 承認が複数並んだとき（実機で見つかった不具合の対策）
更新の承認要求が 2 つ以上並んでいても、安全に扱える。
- **試用期間中は、次の更新を適用できない。** 切り替え直後の版が確定する（30 秒以上正常に動く）まで、次の `update_apply` は拒否される（重ねると、直前の更新が失敗扱いになるため）。
- **前向きの更新だけ。** 動いている版が適用する版の祖先でなければ（古い版・分岐した版）拒否される。古い版へ戻すときは `update_rollback`（これも承認が必要）を使う。
- 承認画面には、複数の承認要求のうち、古いものも残る。迷ったら、一番新しい版（「更新」タブの「最新」）の 1 つだけを承認する。

## 制約・注意
- テストが通ることが適用の条件。テストで検出できない不具合は、試用期間のヘルスチェックと自動ロールバックが最後の安全網になる。
- `supervisor.py` 自体の更新は自動では行わない（見張り役が更新で壊れると戻せないため）。変更があったときは、手動で置き換える。
- 更新元が GitHub のとき、準備でテストを動かす Python 環境に pytest が必要。
- リポジトリ名を変更したときは、`[update] remote_url` を新しい URL に変える（旧 URL も GitHub が自動転送する）。
